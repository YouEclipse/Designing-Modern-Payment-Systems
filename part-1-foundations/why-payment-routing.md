# 第 2 章 为什么需要支付路由

支付路由并不是支付系统一开始就必须拥有的组件。

一家刚上线的电商平台，通常只服务一个市场、接受少量支付方式，并与一家支付服务提供商（PSP）合作。此时最重要的是尽快完成第一笔真实交易，而不是提前搭建一个复杂的决策平台。把所有支付请求发给同一家 PSP，是合理、可维护，而且往往是最正确的起点。

问题在于，业务不会一直停留在这个起点。

当商户进入新的国家，增加本地支付方式，开始比较不同**收单机构**的费率，并要求支付链路达到更高可用性时，“把请求发给谁”就不再是一个写死在代码里的答案。它变成了一个需要结合交易上下文、合同能力、实时健康状态和历史表现做出的决策。

本章从一个只接入单一 PSP 的系统出发。我们会先保留这个设计的优点，再观察它在哪些业务变化下逐步失效，最后推导出支付路由系统的基本形态。这里讨论的是商户或支付平台一侧的**服务商路由**，不是卡组织内部的网络路由。后续章节会分别展开规则引擎、成功率模型、成本模型、幂等、后备切换和可观测性；这一章的目标，是先回答一个更基础的问题：**为什么值得把路由设计成一个独立的系统？**

## 2.1 没有路由服务时，路由仍然存在

假设一家名为 Aurora 的在线票务平台首先在美国上线，只接受美元信用卡，并接入 PSP A。简化后的授权链路如下：

```mermaid
flowchart TB
    Customer["顾客"] -->|"提交支付"| Merchant["Aurora 收银台"]
    Merchant -->|"创建支付"| PaymentAPI["支付 API"]
    PaymentAPI -->|"授权 USD 卡交易"| PSPA["PSP A"]
    PSPA --> Acquirer["收单机构"]
    Acquirer --> Network["卡组织"]
    Network --> Issuer["发卡行"]
```

这里没有名为路由服务的组件，但系统已经做出了路由决策：

```text
所有交易 → PSP A
```

![单 PSP 架构把所有支付隐含地导向 PSP A](../assets/why-payment-routing-illustrations/01-single-provider-one-way.png)

这个决策只是隐含在配置、SDK 调用或业务代码中。只要所有交易都满足同一组假设，它就不需要成为一个独立组件：

- PSP A 支持商户需要的国家、币种和支付方式；
- PSP A 的可用性能够满足业务目标；
- 商户可以接受 PSP A 的费率和结算安排；
- PSP A 对不同客群的授权表现没有重要差异；
- 支付失败时，商户没有另一条可以尝试的处理路径。

单 PSP 架构还有一些常被低估的优点。它只有一套 API 语义、一种错误码体系、一条回调通知链路，以及一套服务商特有的对账语义和报表体系。退款、拒付、结算和客服都可以围绕一个支付服务商建立。此时增加抽象层，反而会提高开发和排障成本。

因此，单 PSP 不是“不够先进”的架构。它是一组业务约束下的最小可行设计。我们需要讨论的，不是如何尽快替换它，而是哪些约束改变后，它不再足够。

## 2.2 第一条裂缝：支付服务商的能力并不等价

半年后，Aurora 准备进入德国和巴西。团队最初设想继续使用 PSP A，只需增加 EUR 和 BRL 两种币种。但接入评估很快暴露出一个问题：不同支付服务商不是只有价格不同的同质化 HTTP API。

它们可能在以下方面具有不同边界：

- 获准处理的商户实体和国家；
- 支持的交易币种与结算币种；
- 银行卡、Pix、iDEAL、钱包等支付方式；
- Visa、Mastercard 或本地卡组织的覆盖；
- 3DS、网络令牌、分期付款、部分请款等能力；
- 单笔限额、风险政策和商户类别限制；
- 本地收单与跨境收单能力；
- 退款、拒付证据和对账数据的完整程度。

支付凭证本身也可能限制候选。由 PSP A 凭证库签发的银行卡令牌，通常不能直接交给 PSP B 使用。商户要在多个支付服务商之间路由同一支付方式，需要预先设计合规的凭证可携带方案，例如受控的独立凭证库与转发机制、服务商支持的迁移机制，或适用场景中的网络令牌。没有可供目标支付服务商使用的凭证，即使它在合同和币种上都合格，也不能成为真实候选。

假设 PSP A 能处理美国和欧洲的银行卡，却不支持 Aurora 巴西实体所需的 Pix；PSP B 在巴西具有本地能力，但不支持德国的某种本地支付方式；PSP C 能覆盖两地，却无法为 Aurora 提供所需的分期产品。此时支付服务商的选择首先是一个**准入筛选问题**，而不是评分问题。

系统要先回答：

> 哪些支付服务商在合同、合规和技术上能够处理这笔交易？

只有进入候选集的支付服务商，才有资格比较成功率、成本和延迟。一个手续费很低但不支持当前币种的 PSP，得分再高也不应该被选中。

![路由先用币种与认证能力筛出可处理交易的支付服务商](../assets/why-payment-routing-illustrations/02-provider-eligibility-key.png)

## 2.3 第二条裂缝：可用性不能由一个外部依赖决定

某个促销日，PSP A 的授权接口开始大量超时。Aurora 自己的支付 API、数据库和网络都正常，但顾客看到的仍然是“支付失败”。从用户视角看，商户的可用性等于整条同步链路中最弱的一环。

接入第二家 PSP 可以降低对单一支付服务商的依赖，但“有两个账号”并不自动带来冗余。两家 PSP 可能共享同一个收单机构、卡组织、云区域或令牌库，因而仍存在共同故障域；备用账号也可能尚未配置足够限额、凭证、回调通知或处理容量。系统还需要知道：

- PSP A 是全局故障，还是仅某个地区、支付方式或端点异常？
- 当前请求是否已经到达 PSP A？
- PSP A 超时前是否可能已经完成授权？
- 哪些失败可以安全地改走 PSP B？
- 切换后，退款、请款和对账应该继续在哪个支付服务商完成？

这里出现了支付可用性与普通读请求故障切换的关键差异。一次支付请求超时，不等于支付没有发生。如果 PSP A 已经获得发卡行批准，只是响应在返回途中丢失，此时把同一订单立即提交给 PSP B，可能形成两次授权，甚至两次扣款。

所以，多支付服务商的价值不是“失败就换一家”这么简单。它要求系统识别结果为成功、明确失败还是未知，并只在语义允许时执行后备切换。[第 10 章](../part-3-reliability/timeout-and-retry.md)、[第 11 章](../part-3-reliability/idempotency.md)与[第 12 章](../part-3-reliability/fallback-routing.md)会完整讨论这条边界。

## 2.4 第三条裂缝：平均成功率会掩盖真正的差异

恢复可用性只是接入多 PSP 的一个原因。Aurora 很快发现，即使 PSP A 和 PSP B 都处于健康状态，它们对不同交易的授权表现也并不相同。

假设最近四周的有效样本显示：

| 交易分段 | PSP A 授权成功率 | PSP B 授权成功率 |
| --- | ---: | ---: |
| 德国发行 Visa，EUR | 94% | 88% |
| 巴西发行 Mastercard，BRL | 72% | 91% |
| 美国发行 Visa，USD | 93% | 92% |

这里的数字只是后续推导使用的示意性快照，不是对真实支付服务商的基准评价。可比较口径至少应限定在同一商户、相同时间窗口、相同首次尝试分母和近似的金额、认证、令牌与风险策略，并同时查看样本量与不确定性；否则，`94%` 与 `88%` 可能只反映两组流量的难度不同。

如果只看全局平均值，PSP A 可能仍然领先。但对于一笔巴西发行的 Mastercard 交易，全局平均值不是最相关的信息。支付服务商与收单路径、发卡行连接、认证方式、请求字段质量以及本地处理能力之间的组合，可能使结果产生明显差异。

于是，决策从：

```text
route() = PSP_A
```

演进为：

```text
route(issuer_country, card_brand, currency, payment_method, merchant) = provider
```

这也是成功率路由的直觉来源：对当前交易，选择预期授权成功率更高的可用路径。然而，历史成功率不是一个可以直接抄进 `if` 语句的常量。样本量过小、数据延迟、客群差异、发卡行响应码口径和路由策略本身造成的选择偏差，都会让指标产生噪声。[第 8 章](../part-2-routing-engine/success-rate-routing.md)会说明如何按分段聚合、平滑和回退，以及为什么不能把短窗口内的偶然波动当成真实优势。

## 2.5 第四条裂缝：最便宜的交易不一定最省钱

支付服务商成本通常同时包含固定费用、按比例费用、跨境费用、币种转换、卡组织费用，以及失败、退款、拒付或附加服务产生的费用。即使暂时把它们简化成一个数字，也不能只比较“每次请求的手续费”。

为了只说明成本口径，先看另一组金额同为 100 EUR、但卡种与风险分段不同的示意性交易。它有两条候选路径：

| 支付服务商 | 单次授权相关预期成本 | 预期成功率 | 每次成功的粗略成本 |
| --- | ---: | ---: | ---: |
| PSP A | 1.10 EUR | 92% | 1.20 EUR |
| PSP B | 0.85 EUR | 75% | 1.13 EUR |

这里假设“单次授权相关预期成本”已经按每次支付尝试计入可能发生的固定和结果相关费用。在这个简化前提下，粗略的 `cost / success_probability` 已经比单看 0.85 EUR 更接近业务问题，但它仍然没有计算支付失败造成的订单流失、重试成本和顾客体验。如果这张票的毛利很高，17 个百分点的成功率差异可能远比 0.25 EUR 的费率差重要；对于低毛利、小额或可延迟支付的场景，结论又可能不同。

因此，成本感知路由的目标不是机械地选择最低费率，而是在合同、成功率和业务价值之间优化预期结果。[第 7 章](../part-2-routing-engine/cost-aware-routing.md)会构建更完整的 `expected_cost(transaction, provider)`，[第 18 章](../part-4-operating-at-scale/settlement.md)则会把路由决策与最终结算和成本归因连接起来。

## 2.6 第五条裂缝：风险不是路由结束后的附加检查

支付路由与风控也不能彼此隔离。某个支付服务商可能支持更完整的 3DS 流程，另一个支付服务商对特定钱包拥有更好的令牌能力；高风险交易可能必须经过额外认证，而低风险、低金额交易可能适合摩擦更小的路径。

风险感知路由不意味着路由服务自己成为完整的欺诈检测系统。更合理的边界是：风控引擎输出结构化信号或约束，路由服务将其作为准入筛选或评分的输入。例如：

```text
risk_action = REQUIRE_3DS
```

会排除无法执行所需认证流程的支付服务商；

```text
risk_action = BLOCK
```

则应该在进入支付服务商选择之前终止交易，而不是寻找一家“更容易通过”的 PSP。风险信号若只是一个可以被成功率权重抵消的软分数，系统可能为了短期转化率绕过本应执行的控制。

这说明路由目标不是单变量最大化。成功率、成本、延迟、风险和合规中，有些是可以权衡的目标，有些则是不可违反的硬约束。生产系统必须明确二者的区别。

## 2.7 从第二个 SDK 到硬编码路由

Aurora 接入 PSP B 后，最直接的实现是把选择逻辑写进支付 API：

```go
func selectProvider(currency, issuerCountry string) string {
	if currency == "BRL" || issuerCountry == "BR" {
		return "psp_b"
	}
	return "psp_a"
}
```

对于两个支付服务商和两三个市场，这段代码清晰、快速，而且容易测试。问题会随着维度增长而出现。德国商户实体希望 EUR 交易优先走 PSP A，某个大商户拥有 PSP B 的单独费率，巴西 Visa 借记卡要走本地路径，PSP A 在周末维护时又需要临时降级。代码很快变成相互覆盖的条件：

```text
merchant × entity × country × currency × payment_method
× card_brand × amount × risk_action × provider_health
```

这不是单纯的代码美观问题。每次费率调整或运营切流都需要修改、测试和部署支付 API；规则冲突只能从条件顺序中推断；事后也很难回答某笔支付究竟命中了哪段逻辑。

```mermaid
flowchart LR
    PaymentAPI["支付 API"] --> Conditions{"大量条件分支"}
    Conditions -->|"US + USD"| PSPA["PSP A"]
    Conditions -->|"BR + BRL"| PSPB["PSP B"]
    Conditions -->|"EUR + 商户 X"| PSPC["PSP C"]
    Health["临时健康状态"] -.-> Conditions
    Contracts["商户合同配置"] -.-> Conditions
    Metrics["历史成功率"] -.-> Conditions
```

硬编码路由的拐点通常不是某个确定的支付服务商数量，而是**路由策略的变更节奏开始快于支付应用的发布节奏**。当运营需要安全地预览、审批、发布和回滚策略，工程团队需要独立演进决策逻辑时，把路由策略从支付执行代码中抽离，才开始产生净收益。

![不断叠加的市场例外让硬编码路由变成难以维护的规则缠结](../assets/why-payment-routing-illustrations/03-hardcoded-routing-tangle.png)

## 2.8 路由层的出现

抽离后的路由服务接收一份路由上下文，返回一个路由决策。它不应该只返回 `psp_b`，还应说明候选如何产生、哪些支付服务商被排除、使用了哪个策略版本，以及决策基于什么信号。

```mermaid
flowchart TB
    Merchant["商户"] --> API["支付 API"]
    API --> Orchestrator["支付编排服务"]
    Orchestrator --> Context["路由上下文构建器"]
    Context --> Router["支付路由系统"]

    subgraph Decision["路由决策"]
        Eligibility["服务商准入筛选"]
        Rules["路由规则"]
        Scoring["服务商评分"]
        Selection["排序后的候选计划"]
        Eligibility --> Rules --> Scoring --> Selection
    end

    Router --> Eligibility
    Config["版本化配置"] -.-> Router
    Signals["健康 / 成本 / 表现 / 风险"] -.-> Router
    Selection --> Store["路由决策存储"]
    Selection --> Orchestrator
    Orchestrator --> Adapters["服务商适配层"]
    Adapters --> PSPA["PSP A"]
    Adapters --> PSPB["PSP B"]
    Adapters --> PSPC["PSP C"]
```

图中使用 `PSP A`、`PSP B` 作为简写。生产系统真正选择的目标通常更具体，例如 `provider_connection + merchant_account + region_endpoint`。同一家 PSP 的两个商户账号可能使用不同合同、币种、凭证和故障域，不应因为品牌相同就被视为同一条路径。

这里有一个重要边界：**路由服务负责选择，支付编排服务负责推进支付状态并执行服务商调用。** 如果路由服务在决策过程中直接发起授权，它就同时承担了策略评估、外部副作用和支付状态机，超时、重试与审计边界都会变得模糊。[第 3 章](routing-system-boundaries.md)会继续讨论路由服务是否应当有状态，以及它与编排服务的职责划分。

一个最小路由决策可以表示为：

```json
{
  "decision_id": "rd_01J...",
  "payment_id": "pay_01J...",
  "selected_provider": "psp_b",
  "candidate_order": ["psp_b", "psp_a"],
  "policy_version": "routing-policy-42",
  "reason_codes": ["BR_LOCAL_ACQUIRING", "HIGHER_EXPECTED_SUCCESS"],
  "experiment": null
}
```

它是一个决策，而不是支付结果。`selected_provider = psp_b` 只说明下一次支付尝试应该走 PSP B，并不说明授权已经成功。一旦授权在某个支付服务商上获批，后续请款、撤销或退款通常必须沿用原支付服务商及其交易引用；它们不是可以重新选择任意 PSP 的一次新路由。

`candidate_order` 也只是生成决策时的条件性候选顺序，不是未来后备切换的执行许可。创建下一次支付尝试前，系统仍须重新验证当前准入条件、风险约束、健康状态，以及前一次支付尝试是否已得到允许重新路由的结果。

## 2.9 路由策略如何逐步演进

路由层出现后，也不应立即变成一个复杂的机器学习系统。更稳妥的演进路径是让策略复杂度跟随问题增长。

### 2.9.1 静态路由

静态路由为稳定分段指定固定支付服务商，例如美国实体默认走 PSP A，巴西实体默认走 PSP B。它可预测、容易解释，适合合同边界明确、流量稳定的场景。它的缺点是不会响应支付服务商状态和表现变化。

静态路由也可以包含简单的优先级列表或固定比例分流，例如 `90% → PSP A, 10% → PSP B`。比例分流适合逐步迁移和积累对照数据，但随机结果必须按 `payment_id` 或稳定哈希保持一致，否则同一笔支付的重试可能意外换路。

### 2.9.2 基于规则的路由

当例外增多，可以把条件与动作抽成带版本的规则：

```text
IF merchant_entity == "aurora_br"
AND currency == "BRL"
AND payment_method == "card"
THEN prefer [PSP_B, PSP_A]
```

基于规则的路由让策略脱离应用发布，但也引入了优先级、冲突、验证、审批和回滚问题。规则引擎不是为了消灭复杂度，而是为了让复杂度可见、可测试、可审计。[第 5 章](../part-2-routing-engine/rule-based-routing.md)将从 `if / else` 继续演进出完整的规则模型。

### 2.9.3 成功率路由

系统可以按交易分段估计每个支付服务商的 `expected_success_rate`，在候选之间偏向更可能被授权的路径。这里要避免两个陷阱：一是小样本把偶然的 100% 当成稳定优势；二是只把容易成功的交易发送给某家支付服务商，再用结果证明它更好。模型需要最小样本、平滑、探索流量和公平的评估口径。

### 2.9.4 成本感知路由

系统可以估算固定费用、比例费用、跨境和外汇转换等成本，再与成功概率和订单价值结合。最低成本可以作为目标，也可以只是评分中的一个因素。合同价目通常有阶梯、返佣和月度承诺，路由时使用的模型还需要与结算后的真实账单校准。

### 2.9.5 风险感知路由

风险信号可以形成硬约束，例如必须支持 3DS，也可以形成软偏好，例如在等价路径中选择令牌能力更完整的支付服务商。路由服务应消费稳定、可解释的风控动作，而不是复制风控引擎的全部特征和模型。

### 2.9.6 失败后的后备路由

后备路由是第一次支付尝试失败后的又一次路由决策。它不能只读取“PSP A 不健康”，还必须读取前一次支付尝试的终态与服务商语义。如果能力不支持是在派发前由本地准入筛选或适配器检出，或者服务商契约明确保证某个错误发生在执行前且没有副作用，系统才可以改选候选；仅凭错误名称不能做此推断。明确的硬拒绝通常不应换 PSP 重试；超时或连接中断造成的未知结果，则应先用相同幂等键重试原支付服务商、查询状态或等待回调通知，不能假设它失败。

不同策略的适用范围可以概括如下：

| 策略 | 主要输入 | 优点 | 主要风险 | 适合的阶段 |
| --- | --- | --- | --- | --- |
| 静态路由 | 国家、实体、币种、固定权重 | 可预测、易解释 | 无法跟随状态变化 | 初期接入、多实体硬边界 |
| 基于规则的路由 | 交易字段、商户配置、优先级 | 灵活、可审计 | 规则冲突与配置爆炸 | 市场和支付服务商增多后 |
| 成功率路由 | 分段历史结果、样本量、时间窗口 | 提高转化潜力 | 噪声、偏差、反馈延迟 | 已有足够多服务商数据 |
| 成本感知路由 | 合同费率、金额、外汇转换、预期成功率 | 控制处理成本 | 成本模型与账单不一致 | 合同和利润目标成熟后 |
| 风险感知路由 | 风控动作、认证能力、合规约束 | 协调转化与风险 | 软分数绕过硬约束 | 风控输出已结构化时 |
| 后备路由 | 支付尝试终态、错误分类、服务商健康状态 | 提高故障韧性 | 未知状态下重复扣款 | 具备幂等和状态查询后 |

这些策略不是互斥选项。生产决策通常先应用硬性准入条件和风险约束，再应用规则，最后在剩余候选中比较成功率与成本。表中的后备路由与前五项并不完全同类：前五项决定初次支付尝试走哪条路径；后备路由是前一次支付尝试之后的恢复策略，只能在失败结果已经被安全分类的前提下重新进入受限决策流程。

## 2.10 一个具体的路由决策

现在看一笔来自 Aurora 巴西站的交易：

```json
{
  "payment_id": "pay_br_2048",
  "merchant_entity": "aurora_br",
  "amount_minor": 52000,
  "currency": "BRL",
  "payment_method": "card",
  "card_brand": "mastercard",
  "issuer_country": "BR",
  "risk_action": "REQUIRE_3DS"
}
```

系统接入了三家支付服务商：

| 支付服务商 | BRL 本地收单 | 支持所需 3DS | 最近分段成功率 | 估算成本 | 当前健康状态 |
| --- | --- | --- | ---: | ---: | --- |
| PSP A | 否 | 是 | 72% | 7.80 BRL | 健康 |
| PSP B | 是 | 是 | 91% | 6.40 BRL | 健康 |
| PSP C | 是 | 否 | 93% | 5.90 BRL | 健康 |

PSP C 的原始成功率最高、成本最低，但它无法完成这笔交易所需的认证，因此在准入筛选阶段被排除。PSP A 和 PSP B 都可用；PSP B 同时具有本地收单、更高的分段成功率和更低的估算成本，于是成为首选。

![PSP C 即使分数诱人，也会因缺少所需 3DS 能力先被硬约束排除](../assets/why-payment-routing-illustrations/04-hard-constraints-before-scoring.png)

这个决策的原因码可以是：

```text
已选择：PSP_B
已排除：PSP_C → REQUIRED_3DS_UNSUPPORTED
首选：PSP_B → LOCAL_ACQUIRING, HIGHER_EXPECTED_SUCCESS, LOWER_EXPECTED_COST
后备：PSP_A → 仅在明确且可安全重新路由的失败后启用
```

下面的 Go 代码刻意保持简单，只展示“先过滤，后评分，最后记录原因”的形态：

```go
package routing

import (
	"errors"
	"math"
)

type Candidate struct {
	Name           string
	Eligible       bool
	SuccessRate    float64 // 取值范围为 0.0～1.0
	NormalizedCost float64 // 0.0 最便宜，1.0 最昂贵
	Degraded       bool
}

type Decision struct {
	Provider string
	Score    float64
	Reasons  []string
}

func Route(candidates []Candidate) (Decision, error) {
	best := Decision{Score: math.Inf(-1)}

	for _, candidate := range candidates {
		if !candidate.Eligible {
			continue
		}

		healthPenalty := 0.0
		if candidate.Degraded {
			healthPenalty = 0.30
		}

		score := 0.70*candidate.SuccessRate -
			0.20*candidate.NormalizedCost -
			healthPenalty

		// 在这个教学示例中，服务商名称是稳定的平局裁决键。
		if score > best.Score ||
			(score == best.Score && candidate.Name < best.Provider) {
			best = Decision{
				Provider: candidate.Name,
				Score:    score,
				Reasons:  []string{"ELIGIBLE", "BEST_COMPOSITE_SCORE"},
			}
		}
	}

	if best.Provider == "" {
		return Decision{}, errors.New("no eligible provider")
	}
	return best, nil
}
```

这不是可用于生产的算法。它没有处理样本置信度、费率单位、硬规则和实验分桶；示例中的名称排序也只是最小化的稳定同分决胜规则，真实系统还要处理配置优先级与版本。权重同样不应在代码中随意写死。它表达的核心顺序是：

1. 不可违反的条件先过滤；
2. 可权衡的目标再评分；
3. 选择结果必须带上可解释依据；
4. 没有合格候选是一个显式结果，不能偷偷回到任意默认 PSP。

后续章节会把每一步替换为可独立测试和演进的组件。

配套代码仓库的[固定实现](https://github.com/YouEclipse/payments/tree/bc4afde24da708d22f67da72a90a1557b1477173/services/router/internal/routing)仍保留本章起点所需的 v1 准入硬约束过滤、版本化静态策略排序与候选排除原因；后续章节推导出的规则、成功率、成本与风险约束则由同一提交中的 v2/v3 流水线实现。这样既能重放简单设计，也不会把章节叙事停留在早期快照。

## 2.11 后备切换为什么必须理解支付尝试

设 PSP B 被选中后，授权请求超时。下面的时序展示了最危险的一种情况：

```mermaid
sequenceDiagram
    autonumber
    participant M as 商户
    participant O as 支付编排服务
    participant R as 路由服务
    participant B as PSP B
    participant A as PSP A

    M->>O: 确认支付
    O->>R: 为支付上下文选择路径
    R-->>O: 首选 PSP B + 备选 PSP A
    O->>B: 授权 attempt_1 + provider_idempotency_key
    alt 已批准
        B-->>O: 已授权
        O-->>M: 授权成功
    else 明确且允许重新路由的失败
        B-->>O: 明确且可安全重新路由的失败
        O->>R: 选择下一个合格候选
        R-->>O: PSP A
        O->>A: 授权 attempt_2
        A-->>O: 已授权
        O-->>M: 授权成功
    else 超时 / 结果未知
        Note over B,O: PSP B 可能已经获得批准，只是响应丢失
        B--xO: 授权响应丢失，attempt_1 进入 UNKNOWN
        O->>B: 复用原操作键重试，或按受支持引用查询
        B-->>O: 最终状态或仍在处理中
        O-->>M: 待定或最终授权结果
    end
```

如果编排服务在超时后直接把交易交给 PSP A，发卡行可能再次批准。两次授权可能先表现为两笔资金保留或待入账记录；若后续又分别请款，才可能形成两笔入账交易。服务商级幂等键通常只在该支付服务商的特定账户、区域和保留期内约束重复请求，不能让 PSP A 识别 PSP B 已处理的交易。因此系统需要区分至少四种身份：

- 商户请求的 `Idempotency-Key`，防止同一次确认被重复创建；
- 内部的 `payment_id` 与 `attempt_id`，区分业务支付和每次服务商尝试；
- 服务商资金操作幂等键，用于在同一支付服务商上重试同一个操作而不重复产生副作用；
- 请求中的商户或服务商引用，用于支付服务商支持的关联或搜索；支付服务商创建交易后返回的交易 ID，则用于状态查询以及后续请款、撤销或退款。这些引用与幂等键不是同一个标识，响应丢失时也可能尚未取得交易 ID。

只有当原支付尝试得到明确、可重新路由的失败，或系统能证明请求没有被支付服务商接受处理时，才应创建指向另一支付服务商的新支付尝试。部分 `5xx`、连接重置和套接字超时都可能属于结果未知；明确的发卡行拒绝也不等于可以任意重试。具体规则还必须结合支付方式、发卡行建议、卡组织当期规则、重试预算和支付服务商 API 语义，不能依赖一张通用的 HTTP 状态码表。

![PSP B 返回结果未知时，系统锁住通往 PSP A 的切换并先查询原交易状态](../assets/why-payment-routing-illustrations/05-unknown-state-stop-fallback.png)

## 2.12 生产环境中的失败模式

支付路由系统引入了更高的控制力，也引入了新的故障面。设计时至少要主动考虑以下场景。

### 支付服务商超时与结果未知

网络超时只描述通信结果，不描述资金结果。系统需要暂停危险的后备切换，通过幂等重试、状态查询、回调通知或对账收敛状态，并给未知结果设置清晰的运营处置流程。

### 指标陈旧或样本失真

昨天的成功率可能无法代表此刻；某个小分段的 4/4 也不能可靠胜过 900/1000。指标服务必须带时间戳、样本量和数据版本。数据过期时，路由服务应回退到稳定策略，而不是继续输出看似精确的分数。

### 健康信号抖动

少量超时可能让所有实例同时摘除 PSP A，把流量瞬间压向 PSP B，随后又因 PSP B 变慢而切回，形成路由振荡。健康判断需要最小样本、迟滞、半开恢复、流量坡度和服务商容量保护，而不是一个共享布尔值。

### 配置错误

一条范围过大的规则可能把全部流量导向未经验证的支付服务商；两条相同优先级的规则可能产生不确定结果。配置平台需要模式校验、冲突检测、影响面预览、审批、灰度、版本化和一键回滚。运行时则应保留最近已知可用配置。

### 依赖失败与级联超时

如果每次路由都同步查询合同数据库、指标仓库和风控引擎，路由服务的可用性会成为这些依赖可用性的乘积。生产路径通常使用版本化快照、本地或分布式缓存，以及严格的延迟预算。哪些信号过期后可以降级、哪些缺失时必须拒绝，需要逐项定义。

### 重复请求、重复回调通知与乱序事件

商户可能重试确认，支付服务商可能重复投递回调通知，状态查询也可能返回比事件流更旧的信息。路由服务的决策、编排服务的支付尝试和最终支付状态必须用幂等写入和单调状态转换连接起来。仅在入口做一次 Redis `SETNX` 并不足以解决整条链路的一致性。

### 优化目标反噬

只优化授权成功率，可能把高风险流量导向更宽松的路径；只优化成本，可能牺牲转化；只看短期转化，又可能忽略拒付和结算损失。目标函数应与业务损益和风险上限一起评审，并通过实验和事后归因校准。

## 2.13 生产环境考量

从上述故障模式，可以得到一组支付路由系统进入生产前必须具备的基本性质。

**确定性与可复现。** 对同一份路由上下文、配置版本和信号快照，路由服务应给出稳定结果。需要随机分流时，使用稳定分桶并记录实验分配。排障人员必须能够重放当时的决策，而不是拿今天的配置猜测昨天发生了什么。

**决策可解释。** 路由决策存储至少记录候选集、排除原因、命中规则、评分摘要、服务商健康快照、配置版本和最终选择。敏感特征应做最小化和脱敏，不能为了审计把完整卡号写进日志。

**低延迟但不依赖实时全量查询。** 路由服务位于同步支付路径中，额外延迟会直接增加顾客等待时间。规则、能力矩阵和聚合指标应以可控新鲜度分发到决策节点；写入分析系统等非关键操作可以异步执行，但核心决策记录不能悄悄丢失。

**安全降级。** 配置服务不可用时，可以继续使用已验证的上一版本；动态成功率过期时，可以回退到静态优先级；关键准入条件或风险约束缺失时，则可能必须按关闭原则拒绝执行。降级策略需要按信号定义，不能统一写成“使用默认 PSP”。

**幂等贯穿调用链。** 商户请求、支付、支付尝试和服务商请求各有不同作用域。路由服务生成新候选不等于授权重试安全；是否创建新支付尝试，应由掌握支付状态的编排服务决定。

**数据边界清晰。** 路由上下文应优先携带支付方式令牌、卡品牌、发卡行国家或受控的 IIN/BIN 派生信息，而不是原始 PAN。令牌化可以减少敏感卡数据在系统中的扩散，但是否缩小 PCI DSS 范围取决于令牌类型、可逆性、系统连接关系和具体实现，不能把“用了令牌”当成自动出域。CVV 等敏感认证数据不应进入路由决策、日志或指标标签，授权完成后也不能为了将来后备切换而保存。

**配置与代码同等严肃。** 路由策略可以不经应用发版而变化，因此它本身就是生产代码。规则需要测试样例、所有者、变更原因、审批记录、生效时间、灰度范围和回滚路径。

**结果闭环。** 一次路由决策只有连接到授权、请款、退款、拒付、结算和真实费用后，才能判断它是否有效。技术可用性、授权批准率、首次尝试成功率与包含恢复后的最终支付成功率是不同指标，不能用一个含混的 `success_rate` 代替。只看入口流量分布，也无法证明策略改善了业务。

## 2.14 支付路由系统的最小职责

走到这里，我们可以给支付路由系统一个初步定义：

> 支付路由系统根据某次支付的上下文、服务商准入条件、版本化策略以及可用的健康、表现、成本和风险信号，选择下一条允许执行的支付路径，并输出足以被系统持久化、解释和重放的路由决策。

这个定义刻意没有说路由服务负责完成支付。完整系统中：

- 支付 API 维护对商户稳定的接口与幂等契约；
- 支付编排服务维护支付和支付尝试状态，决定何时执行、查询或补偿；
- 路由服务产生支付服务商选择及其理由；
- 服务商适配器把统一意图转换成不同 PSP 的 API 语义；
- 对账让内部状态与支付服务商、结算数据最终收敛。

这些边界并非唯一答案，但如果全部压进一个同步服务，任何策略变更都可能触碰资金状态机，任何支付服务商差异也可能污染全局决策逻辑。[第 3 章](routing-system-boundaries.md)将专门检验这些边界，并讨论路由服务应该保存什么、不应该保存什么。

## 2.15 小结

我们没有从“需要一个规则引擎”开始，而是从一个完全合理的单 PSP 系统开始。

当业务只有一个市场、一组支付方式和一条处理路径时，隐含规则 `all → PSP A` 足够简单。随着国家、币种、商户合同和支付方式增加，支付服务商先表现出准入条件差异；随着可用性要求提高，系统需要冗余，却又必须面对结果未知状态下的重复扣款风险；随着交易数据积累，成功率、成本和风险开始要求更细粒度的选择。

硬编码 `if / else` 可以支撑早期阶段，但当策略变化快于应用发布、决策需要审计和回放时，路由策略就需要从支付执行代码中抽离。由此得到的路由服务不是一个随机选择 PSP 的负载均衡器，而是一个受硬约束控制、使用版本化策略、产生可解释决策的支付决策系统。

[下一章](routing-system-boundaries.md)将进一步收紧系统边界：支付编排服务与路由服务分别拥有什么状态？路由服务是否应该调用 PSP？一次路由决策与一次支付尝试如何对应？只有先回答这些问题，后续的规则引擎、动态评分和后备切换才不会建立在模糊的资金语义之上。
